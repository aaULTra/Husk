# M3 / M7 / M8 / M9: CyPort source comparison

Reviewed public Thijs2004/CyPort, main SHA 65e2e57a95263f60516f567e274780d8ebd97072, README.md and shim/MacShim.m / MacShimC.c. This is source investigation, not independent reproduction of its performance claims. CyPort runs the Mac Cyberpunk 2077 build; Husk runs Android Dungeons through different engine/driver/compatibility paths. Do not copy game-specific thresholds or infer core placement from QoS.

| CyPort mechanism observed | Husk relevance and status | Acceptance / next action |
| --- | --- | --- |
| Named redDispatcher worker QoS split; configurable fast-worker budget | M7: related idea already exists in guarded Adaptive Trial. Dungeons normal/background roles and CPU-capacity hint differ. Balanced is already Default/Utility in device logs. | Confirm actual admission/application and energy A/B against Balanced; no presumed efficiency-core pinning or priority increase |
| Repeated sched_yield backoff after a consecutive-yield threshold | M8: potentially useful only if Dungeons burns meaningful time yielding. This candidate adds observation counts to the guest import and explicit syscall paths while monitoring is active, without backoff or clocks/sleeps. | Relate yield rate to CPU/pacing traces; only then design a reversible backoff experiment. Counts alone do not establish wasted cycles. Internal host spins and all guest inline locks are not covered. |
| Converts requested real-time scheduling to normal policy | Husk already ignores observed guest scheduler-policy setters in its compatibility shims; no corresponding active real-time starvation is established. | Audit/profile actual scheduling before adding another policy rewrite. Preserve critical roles. |
| Hooks Metal command-buffer commit, attaches completion handlers, reads GPUStartTime/GPUEndTime, merges intervals over short sampling periods | M3: concrete alternative to Instruments or a custom driver build, but needs safe game/queue attribution in LiveContainer, correct method chaining/lifetime and measured overhead. Current public Vulkan wrapper still does not supply completed Metal buffers. | Investigate scoped interception separately; do not blanket-hook all host Metal work. Clip/merge intervals to explicit sample bounds, disclose buffer drops/late completions and do not call sampled game-buffer coverage device-wide utilisation. No implementation in this candidate. |
| Streaming work budget/user.ini tuned for Cyberpunk | Game-specific REDengine behaviour, not a portable Dungeons patch | UE4 asset/streaming changes require their own traces and image/correctness tests |
| Existing native game MetalFX path with a capability compatibility override | M9: Cyberpunk already has upscaling inputs/renderer integration. Husk's final Vulkan presenter does not. | Actual capability detection is implemented, but spatial interop prototype still needs inputs, texture ownership/sync/color-space/UI quality checks and GPU/power benefit |
| Frame pacing/present hooks and variable caps | M4: mechanism is relevant, but requested target stays 60 FPS. Default-off engine-only comparison is now available. | Independent matched A/B; do not import 40 FPS defaults, extra spin or cap-margin tuning without evidence |

Sequence: corrected M1 measurements -> M2 shader groups and M3 GPU/CPU/wait trace -> independent M4/M7/M8 experiments -> M9 prototype when GPU evidence and safe interop design justify it. M9 need not wait for every later research experiment. All device energy benefits remain unverified.

The new guest_yield_calls_cumulative field is MEASURED API-path count, tagged M8 in metric_plan_ids. It is not a spin-duration or power measurement. It is collected only in included monitored spans, leaves native sched_yield and worker checkpoints unchanged, and adds no per-yield log or timestamp. Test monitoring-on/off/exclusion behaviour before using count-rate comparisons.
