## What the CPU evidence newly establishes

Actual sampled CPU counter deltas identify an **unnamed thread** at19.90% of one CPU in A/20.52% in B; RHIThread10.47/10.58%;RenderThread1 9.43/9.23%. The unnamed thread's guest/host role is not proven. Do not call it the game thread or change its priority based only on rank. Mach thread IDs and worker-observer identities are different namespaces; they must not be joined by their numeric value. A next substantial diagnostic/engineering batch can label the known guest entry thread or export an explicit identity mapping if needed; no per-frame collector is required.

Four named TaskGraphNP workers together account for1.830/1.760% of one CPU over their matched snapshot spans, approximately2.93/2.77% of **matched thread CPU time**. This makes ordinary TaskGraph worker CPU time a small part of the observed process work in these runs, unlike assuming all workers dominate CPU time. It is not an electrical-energy share, no P/E residency is measured, and QoS can change frequency/energy without a matching CPU-time reduction. Do not mark CyPort-style placement, mode4 or strict Adaptive efficient from this data. Critical/high-priority workers remain preserved.

Only~5.6–5.8% of recorded submit caller wall is caller-thread CPU. The rest may include blocking,descheduling,GPU/presentation back-pressure or work elsewhere. This is strong reason to stop interpreting7–9ms synchronous submit wall as equivalent expensive CPU encoding or pure GPU execution. Durations can overlap; never add wall waits across calls to claim exclusive frame time or watts. GPU sampling was OFF, so dominant GPU execution versus synchronisation is still unresolved.

M8 slow-path sync counters are zero in both included sessions. Completed-once fast calls are deliberately uncounted; setup/initialisation may have occurred before capture.
